## Review Focus

- A bar being dragged must not jump rows mid-drag.
- Undo of a region change must not disturb drawings, and undo of a drawing must not disturb regions made before it (each snapshot restores both to that point in time).

- A callout moved or scaled with the Select tool must sit in the same place after an edit that changes only the text.

### Task 3: Even frame steps around a freeze inside a speed region

**Files:**
- Modify: `src/export/outputTimeline.ts` (`playSegments`, `speedSegmentFrame`, `frameSourceTimes`, `framePresentations` as needed), `electron/clipExport.ts` (`speedSegmentChain`, segment validation), the `OutputSegment` type where it is declared (both the renderer and the electron copy)
- Test: `src/export/outputTimeline.test.ts`, the existing clipExport test file

**Interfaces:**
- `OutputSegment` play variant gains an optional `phase?: number` (source frames, `0 <= phase < speed`-scale; absent means 0). The shared frame rule becomes: output frame `f` of a segment over source frames `[a, b)` with `n` planned frames and phase `p` shows `a + floor((f * (b - a) + p) / n + 1e-6)`, clamped to `b - 1`. With `p` absent the rule and every generated filter string are exactly today's.

- [ ] **Step 1: Reproduce.** Write a test in `outputTimeline.test.ts`: source 30 fps, output 30 fps, one 2x region over source frames 30–60 (use the real `buildSpeedSteps` so the ramp steps are included), a hold of 1 s at a source frame in the constant-2x part chosen so the first half has an odd number of source frames. Collect `frameSourceTimes`, convert to source frame indices, and assert that within the constant-2x part the differences between consecutive play frames are all exactly 2, ignoring the repeated hold frames. Confirm it fails today and record the actual sequence in your report.
- [ ] **Step 2: Decide the phase.** For consecutive play segments of the same speed separated only by holds, the second segment's phase continues the first one's grid: the first source frame it shows is the one the unsplit segment would have shown next. Derive `phase` in `playSegments`/`buildOutputTimeline`; segments not preceded by a hold inside the same speed step get no `phase` field at all.
- [ ] **Step 3: More failing tests:** 0.5x with a hold (each source frame shown exactly twice on both sides); 2x with two holds in one region; a hold exactly on a step edge (no phase emitted); a timeline with speed regions and no hold → `buildOutputTimeline` output deep-equals a snapshot taken before your change (no `phase` keys anywhere); frame counts still sum to `round(duration * fps)`.
- [ ] **Step 4: Implement** the renderer side, then mirror the rule in `speedSegmentChain` (the `setpts` expression) and accept `phase` in segment validation (finite number, `>= 0`). Add a clipExport test that a segment without `phase` yields the identical filter string as before, and one with `phase` yields the shifted expression.
- [ ] **Step 5: Real ffmpeg check.** Write a throwaway script in the scratchpad (not in the repo) that builds a 3 s 30 fps test video with a burned-in frame counter using the `ffmpeg-static` binary in `node_modules`, runs the real filter graph for the Step 1 case and the 0.5x case, extracts the output frames' source indices (e.g. via a per-frame unique solid colour or `drawtext` counter decoded with `signalstats`/pixel reads) and compares them with `frameSourceTimes`.
